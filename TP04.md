## 2. Questions obligatoires

### Q1 — Mirror/RAID = Backup ?
Non. Un mirror protège contre la panne d'un disque (la disponibilité), pas contre la perte des données :
- Panne d'un disque : protégé, la copie sur l'autre disque reste disponible (pool `DEGRADED`, comme vu dans notre test).
- `rm -rf`, suppression d'une VM, ransomware : non protégé, l'effacement ou le chiffrement est écrit immédiatement sur les deux disques.
- Vol du serveur, incendie : non protégé, les deux disques disparaissent avec la machine.

Une sauvegarde est une copie indépendante (autre support, idéalement autre lieu) et historisée.

### Q2 — Snapshot = Backup ?
Non. Un snapshot est stocké dans le même pool que les données : `tank/tp04-demo@before-change` se trouve sur les deux disques du mirror `tank`, et ne contient que les blocs référencés par le pool (Copy-on-Write, USED 0B`, `REFER 96K dans notre test). Si tank est  perdu (deux disques HS), les données **et** leurs snapshots disparaissent ensemble. Un snapshot protège d'une erreur de manipulation (rollback vers un état précédent), pas de la perte du stockage. Pour une vraie copie, il faut l'envoyer ailleurs (`zfs send`, réplication vers un autre nœud, sauvegarde PBS).

### Q3 — Pourquoi un pool presque plein (> 80-90 %) est-il dangereux ?
- Copy-on-Write : ZFS écrase pas un bloc, il écrit la nouvelle version ailleurs puis libère l'ancienne. Même pour modifier ou supprimer, il lui faut de l'espace libre.
- Snapshots : ils conservent les anciens blocs. L'espace n'est libéré qu'à la suppression du snapshot, donc un pool peut se remplir alors qu'on a « supprimé » des données.
- Fragmentation : avec peu d'espace libre, ZFS trouve des zones libres de plus en plus morcelées, ce qui dégrade fortement les performances (on recommande de garder de l'ordre de 20 % libre).
- Nouvelles écritures : à 100 %, les écritures échouent (plus d'espace), et même supprimer devient difficile. Avec du thin provisioning (`sparse 1`), les VM croient disposer de plus d'espace que le pool n'en a réellement, et risquent des erreurs d'I/O quand il est plein.

### Q4 — Local ou partagé ?

Non. `zfs-lab` apparaît partout parce que sa configuration est dans `/etc/pve/storage.cfg`, répliqué par pmxcfs, mais les données sont locales : chaque nœud possède son propre pool `tank` et son propre `tank/vmdata`. Le disque d'une VM créée sur PVE01 est dans le pool de PVE01 et n'est pas visible depuis PVE02. La VM ne peut donc pas démarrer immédiatement sur PVE02 « avec le même disque ». Il faut soit copier le disque (migration avec disques locaux), soit répliquer les données régulièrement vers l'autre nœud (réplication ZFS, prévue au TP06), soit utiliser un vrai stockage partagé (NFS, Ceph, iSCSI). Avec de la réplication, une reprise après panne ne restitue que les données de la dernière réplication.

### Expert 2 — Analyse des propriétés ZFS

```bash
zfs get compression,compressratio,recordsize tank/tp04-demo
```

```text
NAME            PROPERTY       VALUE           SOURCE
tank/tp04-demo  compression    lz4             local
tank/tp04-demo  compressratio  1.00x           -
tank/tp04-demo  recordsize     128K            default
```

- **`compression` :** Algorithme sélectionné (`lz4`), rapide et transparent pour le CPU.
- **`compressratio` :** Ratio de réduction volumique ($TailleLogique / TaillePhysique$).
- **`recordsize` :** Taille maximale d'un bloc de données logique pour les datasets (128 Ko par défaut).

> **Pourquoi un serveur de fichiers séquentiel et une base de données n'ont-ils pas les mêmes besoins ?**
> - **Serveur de fichiers séquentiel (ISO, streaming, sauvegardes volumineuses) :** Nécessite un `recordsize` important (1 Mo) pour maximiser le débit séquentiel et limiter la taille de l'arbre de métadonnées.
> - **Base de données relationnelle (PostgreSQL, MySQL / InnoDB) :** Écrit sur de petites pages de 8 Ko ou 16 Ko. Un `recordsize` conservé à 128 Ko crée un phénomène d'**amplification d'écriture** (*Write Amplification*) : modifier une entrée de 8 Ko contraint ZFS à relire et réécrire 128 Ko entiers sur disque. Le `recordsize` doit être calé sur la taille de page du moteur.

> **Un serveur ZFS qui utilise beaucoup de RAM est-il en manque de mémoire ?**  
> **Non.** L'ARC consomme par conception la mémoire vive non allouée pour mettre en cache les blocs les plus sollicités (MFU) et récents (MRU). Cette mémoire reste classée comme restituable : dès que le système hôte ou une VM réclame de la RAM, le mécanisme d'éviction du noyau ZFS libère immédiatement ses pages de cache pour éviter tout blocage ou incident lié à l'OOM-Killer.

### Expert 4 — Synthèse stockage

| Mécanisme | Objectif principal | Description |
| :--- | :---: | :--- |
| **MIRROR** | **B** | Continuer à disposer des données malgré la panne d'un disque |
| **SNAPSHOT** | **A** | Revenir rapidement à un état précédent |
| **REPLICATION** | **C** | Disposer d'une copie des données sur un autre nœud |
| **BACKUP** | **D** | Restaurer depuis une copie indépendante |
| **HA** | **E** | Remettre automatiquement le workload en service après une panne |



### Question

Un serveur ZFS qui utilise beaucoup de RAM est-il forcément en manque de mémoire ? Justifiez.

Non, un serveur ZFS qui utilise beaucoup de RAM n'est absolument pas en manque de mémoire. C'est même le comportement normal et souhaité.

Voici pourquoi, en nous basant sur vos propres résultats :

### 1. La philosophie ZFS : "La RAM inutilisée est de la RAM gaspillée"

ZFS utilise la mémoire vive pour stocker son cache de lecture, appelé l'**ARC** (_Adaptive Replacement Cache_). Au lieu de laisser la RAM vide, ZFS va l'occuper autant que possible avec les données récemment et fréquemment lues pour accélérer drastiquement les futures lectures.

Cependant, **ce cache est dynamique**. Si le système d'exploitation ou vos machines virtuelles (puisque vous êtes sous Proxmox, `pve04`) ont soudainement besoin de mémoire, ZFS va immédiatement "vider" son cache et rendre la RAM au système.
