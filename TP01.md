## Questions : 

**Question 1 : hostname vs hostname -f**

hostname renvoie le nom court de la machine (`pve04`), tel qu'il est défini dans `/etc/hostname`. hostname -f renvoie le FQDN, c'est-à-dire le nom complet avec le domaine (pve04.novacorp.lab). Ce FQDN n'est pas stocké quelque part : il est obtenu en résolvant le nom court, ici grâce à la ligne de /etc/hosts. Si cette ligne est incohérente, hostname -f renvoie un mauvais résultat ou une erreur.

**Question 2 : importance de /etc/hosts dans un cluster**

Un nœud Proxmox doit pouvoir résoudre son propre nom vers sa vraie IP (192.168.200.11 pve04.novacorp.lab pve04`), et non vers `127.0.0.1. 
Cette résolution est utilisée par :

- les certificats TLS, dont le nom et l'IP figurent dans les SAN ;
- la jonction au cluster (pvecm add) et les échanges SSH entre nœuds ;
- pmxcfs et Corosync, qui identifient les nœuds par leur nom.

Une entrée erronée provoque des erreurs de certificat, d'identification ou de jonction au cluster

**Question 3 : default via ... dans  ip route**

C'est la route par défaut : la passerelle vers laquelle part tout paquet dont la destination ne correspond à aucune route plus précise. Ici, default via 192.168.200.2 dev vmbr0` envoie tout ce qui n'est pas dans `192.168.200.0/24` vers la passerelle NAT de VMware, par le bridge vmbr0`.

**Question 4 :  vmx / svm dans /proc/cpuinfo**

Ce sont les flags des extensions de virtualisation matérielle : vmx` pour Intel VT-x, `svm pour AMD-V. Leur présence prouve que le CPU (ici virtuel) expose la virtualisation à l'OS invité, condition pour que KVM fonctionne. Le résultat `8` s'explique ainsi : `vmx` apparaît deux fois par vCPU (lignes `flags` et `vmx flags`), soit 4 vCPU × 2.

**Question 5 : rôle des services**

| Service     | Rôle                                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------ |
| pveproxy    | Proxy HTTPS de l'API et de l'interface web (port 8006)                                                             |
| pvedaemon   | Daemon de l'API : exécute les actions privilégiées et les tâches (démarrage de VM, etc.)                           |
| pvestatd    | Collecte périodiquement l'état des ressources (nœud, VM, stockages) pour l'interface et les statistiques           |
| pve-cluster | Lance pmxcfs, le système de fichiers `/etc/pve`, qui stocke la configuration et la réplique entre nœuds en cluster |

**Question 6 : pourquoi exit code 100 ne suffit pas

Le code 100 est le code d'erreur d' apt-get` quand une étape échoue. Il ne dit ni quel dépôt est en cause, ni pourquoi. La vraie cause n'apparaît que dans la sortie complète lancée dans le terminal. Ici, c'était`401 Unauthorized` sur `enterprise.proxmox.com` : le dépôt Enterprise était actif sans souscription.

### Questions du TP

**Pourquoi la route par défaut doit-elle passer par le NAT et non par le LAB ?**

Le réseau NAT est le seul qui donne accès à Internet (apt, DNS, download.proxmox.com`). Le réseau LAB est un underlay interne entre PVE : il n'a pas de gateway et ne sert qu'à la communication entre nœuds (Corosync, migrations). Une route par défaut vers le LAB ferait perdre l'accès à Internet, et avoir deux routes par défaut créerait des conflits.

**Pourquoi la nested virtualization est-elle indispensable ?**

Chaque PVE est déjà une VM (sous VMware Workstation), et il doit à son tour exécuter des VM. Sans VT-x exposé à l'invité, KVM ne peut pas s'activer : les VM seraient émulées en logiciel, extrêmement lentes ou inutilisables. Pour le cluster, la migration et la HA des TP suivants, il faut donc que chaque nœud fasse tourner de vraies VM KVM.

**Pourquoi /etc/pve est-il différent d'un répertoire classique ?**

Ce n'est pas un dossier sur disque mais un système de fichiers virtuel **FUSE** (/dev/fuse on /etc/pve type fuse), fourni par pmxcfs (le processus de pve-cluster). Son contenu est stocké dans une base SQLite et chargé en mémoire. En cluster, il est répliqué en temps réel sur tous les nœuds via Corosync : une modification faite sur un nœud apparaît sur les autres. C'est ce qui donne un point de configuration unique pour tout le cluster.

**Certificat : hostname et FQDN présents ? Pourquoi c'est important ?**

Oui : `CN=pve04.novacorp.lab`, et les SAN contiennent `DNS:pve04`, DNS:pve04.novacorp.lab et IP:192.168.200.11. Lors d'un pvecm add, le nœud qui rejoint se connecte en HTTPS à l'API d'un membre et vérifie son certificat (nom et empreinte). Si le nom utilisé ne figure pas dans le certificat, ou si le hostname a changé après l'installation, la vérification échoue. Une fois le nœud dans le cluster, il reçoit un certificat signé par la CA du cluster.

**Ce que nous avons compris

- L'identité d'un nœud repose sur trois éléments cohérents : hostname, FQDN et /etc/hosts. Ils conditionnent les certificats TLS et la future jonction au cluster.
- Sous Proxmox, l'IP est portée par un bridge (vmbr0) et non par la carte physique, qui en est seulement un port. Cela prépare les VM et le TP02.
- Le chemin Internet (NAT, vmbr0) est distinct du futur réseau LAB : la route par défaut doit rester sur le NAT.
- La virtualisation imbriquée (vmx, module kvm_intel) est indispensable pour que le nœud exécute des VM KVM.
-  /etc/pve est un système de fichiers virtuel (pmxcfs), qui deviendra un espace de configuration répliqué entre les nœuds en cluster.
- Une erreur d'interface (exit code 100) ne suffit pas au diagnostic : il faut relancer la commande dans le terminal et lire le message complet.
- Le nœud reste volontairement vide et non mis à jour avant le cluster : cluster d'abord, workloads ensuite, versions homogènes.
