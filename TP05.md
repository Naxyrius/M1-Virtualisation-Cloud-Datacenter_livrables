## Architecture / configuration

Nœud `pve02.novacorp.lab`, membre du cluster `novacorp-g12` (4 nœuds).

- Stockage des workloads : `zfs-lab`, dataset `tank/vmdata` en `sparse 1`, local au nœud
- Pool ZFS `tank` : miroir de deux disques virtio de 20 Go (`ZFS-DISK1`, `ZFS-DISK2`)
- Réseau des workloads : `vmbr10`, bridge sans port, `10.50.0.1/24`, NAT vers `vmbr0`
- VM `112` `labvm01` et CT `212` `labct01` (à la place des IDs 110 et 210 de l'énoncé)
- Template `9002` `debian13-cloud` et clone `122` `web01` (à la place de 9000 et 111)

Plan d'adressage `vmbr10` (pas de DHCP) :

- pve02 (passerelle) : 10.50.0.1/24
- labvm01 : 10.50.0.10/24, gateway 10.50.0.1, DNS 1.1.1.1
- web01 : 10.50.0.11/24, gateway 10.50.0.1
- labct01 : 10.50.0.21/24, gateway 10.50.0.1, DNS 1.1.1.1

`vmbr10` a été passé de `manual` à `static` avec NAT, en accord avec le formateur, pour que les
workloads puissent joindre Internet (installation Debian netinst, `apt install qemu-guest-agent`).

```
auto vmbr10
iface vmbr10 inet static
	address 10.50.0.1/24
	bridge-ports none
	bridge-stp off
	bridge-fd 0
	post-up echo 1 > /proc/sys/net/ipv4/ip_forward
	post-up iptables -t nat -A POSTROUTING -s 10.50.0.0/24 -o vmbr0 -j MASQUERADE
	post-down iptables -t nat -D POSTROUTING -s 10.50.0.0/24 -o vmbr0 -j MASQUERADE
```

**Question : deux VM connectées à `vmbr10` mais situées sur deux PVE différents peuvent-elles
communiquer directement ?**

Non. `vmbr10` est un bridge sans port physique (`bridge-ports none`) : c'est un segment L2 local à
chaque hôte. Les `vmbr10` de deux PVE sont deux switchs distincts portant le même nom, sans lien L2
entre eux, donc les trames (ARP compris) ne quittent jamais l'hôte, même si les VM sont dans le même
sous-réseau. Le problème n'est pas une absence de route : deux VM du même sous-réseau n'ont besoin
d'aucune route pour se parler. Pour les faire communiquer, il faut étendre ce L2 entre les nœuds
(uplink physique ou VLAN, ou overlay VXLAN via le SDN Proxmox).

Conséquence pour la HA : une VM sur `vmbr10` peut redémarrer sur un autre nœud (si son disque y est
disponible et qu'un `vmbr10` existe), mais elle s'y retrouve isolée des VM restées sur l'ancien nœud.
Le NAT ajouté sur pve02 ne change rien : il donne l'accès à Internet, pas un L2 partagé entre nœuds.

### Partie 7 : Comparaison VM / LXC

Mesures relevées sur pve02, les deux workloads démarrés :

Relevé sur pve02, les deux workloads démarrés : la VM tourne sur son propre kernel
(`6.12.111+deb13-amd64`) alors que le CT affiche celui de pve02 (`7.0.14-19-pve`). Le processus `kvm`
occupe 272 Mo sur l'hôte contre 17 Mo pour le CT, avec 74 processus dans la VM contre 16 dans le CT.
`systemd-analyze` donne 4,6 s de démarrage pour la VM (1,9 s kernel + 2,7 s userspace) et 0,97 s pour
le CT, qui n'a pas de kernel à démarrer.

| Caractéristique | VM KVM | LXC |
|---|---|---|
| Kernel propre | Oui, kernel de l'invité | Non, kernel partagé avec l'hôte |
| OS complet | Oui : firmware, bootloader, kernel, userspace | Non : userspace seul |
| Isolation | Forte, matériel virtualisé par KVM/QEMU | Plus faible : namespaces, cgroups, AppArmor, UID décalés |
| Temps de démarrage | Plusieurs secondes (boot complet) | Environ 1 s (démarrage des services seuls) |
| Consommation RAM | Élevée : kernel, cache et RAM réservée par QEMU | Faible : seulement les processus du conteneur |
| Peut exécuter Windows | Oui | Non, Linux uniquement (kernel de l'hôte) |
| Accès matériel complexe | Oui : passthrough PCI/USB, modules kernel propres | Limité : pas de modules kernel, accès aux périphériques à déléguer |
| Densité de workloads | Plus faible | Plus élevée |

### Partie 8 : Choix d'architecture

| Workload | Choix | Justification |
|---|---|---|
| Active Directory | VM | Contrôleur de domaine Windows Server, impossible en LXC. Même avec Samba AD sous Linux, l'annuaire est critique (Kerberos, réplication) : isolation forte, kernel propre, sauvegardes cohérentes et migration à chaud |
| Nginx stateless | LXC | Service Linux léger sans état : pas besoin de kernel propre, démarrage en une seconde, quelques Mo de RAM. Clonable et jetable, le kernel partagé est acceptable pour un frontal sans données |
| PostgreSQL critique | VM | Isolation forte et ressources garanties. Réglages kernel propres à la base (`sysctl`, huge pages, ordonnanceur I/O) impossibles dans un conteneur qui partage le kernel de l'hôte. Sauvegardes cohérentes via le freeze du Guest Agent |
| Runner CI | VM | Exécute du code non maîtrisé (builds, tests, souvent Docker) : un job malveillant ne doit pas atteindre le kernel de l'hôte. VM facile à jeter et recréer |
| Docker host | VM | Docker a besoin de cgroups, namespaces, overlayfs et privilèges difficiles à accorder dans un LXC (nesting, AppArmor, overlayfs sur ZFS). Déconseillé par Proxmox, une VM fournit son propre kernel |
| DNS cache | LXC | Service réseau Linux minimal et sans état : consommation très faible, démarrage immédiat, forte densité. Se recrée trivialement |
| Appliance propriétaire | VM | Image éditeur (OVA, ISO, qcow2) avec son propre OS et kernel, parfois non Linux, prévue pour du matériel virtuel standard. Le support éditeur l'exige |
| Serveur Windows | VM | Windows a besoin de son kernel NT : un LXC partage le kernel Linux de l'hôte et ne peut pas l'exécuter |

## Questions obligatoires

### Question 1 : VM ou LXC ?

Le choix dépend du besoin en isolation et en kernel. Une VM embarque son propre kernel sur du matériel
virtualisé : elle isole fortement, accepte n'importe quel OS (Windows, appliance) et un kernel réglé
pour le service, au prix de plus de RAM et d'un démarrage plus long. Un LXC partage le kernel de l'hôte :
il est léger et dense mais limité à Linux, et une faille du kernel touche directement l'hôte.

Sur pve02, pour le même Debian 13, la VM 112 occupe 272 Mo et démarre en 4,6 s, le CT 212 occupe 17 Mo
et démarre en moins d'une seconde. On réserve donc la VM aux services critiques, non Linux ou exposés
(AD, PostgreSQL, runner CI, Docker), et le LXC aux services Linux légers et de confiance (Nginx, DNS
cache).

### Question 2 : Template vs snapshot

Un snapshot est un point de restauration d'une VM : il fige son état à un instant pour pouvoir y revenir
(avant une mise à jour par exemple). Il appartient à la VM, la VM continue de tourner et d'évoluer, et
il ne sert pas à créer d'autres machines.

Un template est une VM figée qu'on ne démarre plus : son disque passe en lecture seule
(`base-9002-disk-0`) et elle sert de modèle pour créer de nouvelles VM par clonage. Le snapshot sert à
revenir en arrière sur une machine, le template à en produire d'autres.

### Question 3 : Template vs clone

Le template est le modèle, immuable, et chaque clone est une VM indépendante créée à partir de lui, avec
son propre VMID, sa MAC, son disque et sa configuration Cloud-Init (hostname, IP). Ici, le template 9002
a produit web01 (122), app01 (132) et db01 (142), chacun avec sa propre IP (`10.50.0.11` à `.13`).

Avec `--full 1`, chaque clone reçoit une copie complète du disque et ne dépend plus du template : ZFS
n'indique aucune origine pour `vm-122-disk-0`, `vm-132-disk-0` et `vm-142-disk-0`. Un linked clone
partagerait au contraire les blocs du template et en resterait dépendant.

### Question 4 : Cloud-Init

Non, Cloud-Init n'installe pas Debian. Debian est déjà installé dans l'image genericcloud, que l'on
importe comme disque. Cloud-Init est un service présent dans cette image qui, au premier démarrage, lit
les données du lecteur fourni par Proxmox (`ide2`, `vm-122-cloudinit`) et personnalise la machine :
hostname, utilisateur `student`, clé SSH, IP, passerelle, DNS, mise à jour des paquets. Il détecte une
nouvelle machine grâce à l'`instance-id`, différent pour chaque clone, et ne rejoue donc pas cette
configuration aux démarrages suivants.

### Question 5 : Pourquoi une clé SSH ?

Un mot de passe root identique partout est un secret unique : s'il fuit ou est deviné, toutes les
machines sont compromises en même temps, et il peut être attaqué par force brute sur chaque serveur
exposé. Changer ce mot de passe oblige à repasser sur toutes les machines.

Avec une clé, seule la partie publique est déposée sur les VM, la clé privée ne quitte jamais le poste,
et elle ne peut pas être devinée. On peut désactiver l'accès par mot de passe, révoquer une clé sans
toucher aux autres, et identifier qui se connecte. Enfin, la connexion se fait avec `student` et non
root : l'élévation passe par `sudo` et reste tracée dans les journaux.

### Question 6 : Stockage local

Adapté à notre groupe : le template est `9002` sur pve02.

Non. `zfs-lab` est un stockage local : le disque du template, `base-9002-disk-0`, n'existe que dans le
pool `tank` de pve02. Les autres nœuds ont un stockage portant le même nom mais pas ce disque. Proxmox
n'autorise le clonage vers un autre nœud (`qm clone --target`) que si le disque est sur un stockage
partagé. Il faut donc cloner sur pve02 puis migrer la VM (TP06), répliquer le disque avec ZFS, ou
recréer le template sur chaque nœud.

## Difficultés rencontrées

- **Syntaxe de l'énoncé** : `qm set 110 --scsi0 zfs-lab:8 --discard on --ssd 1` échoue
  (`Unknown option: discard`, `Unknown option: ssd`). `discard` et `ssd` sont des propriétés du disque :
  `--scsi0 zfs-lab:8,discard=on,ssd=1`.
- **`WARN: Systemd 257 detected. You may need to enable nesting.`** à la création du CT : systemd 257
  (Debian 13) a besoin de `nesting` dans un conteneur non privilégié. La GUI l'active par défaut, pas
  `pct create` : ajout de `--features nesting=1`.
- **`ip=dhcp` dans l'exemple `pct create`** : aucun DHCP sur `vmbr10`, le CT resterait sans IP. IP
  statique `10.50.0.21/24`, gateway `10.50.0.1`.
- **IDs de l'énoncé déjà pris** : les VMID sont uniques dans tout le cluster, et 111 est utilisé par
  `labvm11` sur pve01. Template en 9002 et web01 en 122.
- **IP héritée du template** : `ipconfig0` défini sur le template est copié dans chaque clone, il faut le
  redéfinir sur chaque clone pour éviter deux VM en `10.50.0.11`.
- **Faute de frappe sur db01** : `qm set 142 --ipconfig0 ip=10.50.0.12/24` donnait à db01 l'IP de
  app01, corrigé en `10.50.0.13` avant le premier démarrage.
- **Pas de Guest Agent dans les clones** : l'image genericcloud ne fournit pas `qemu-guest-agent`, donc
  `qm agent 122 ping` échoue et `qm shutdown` retombe sur l'arrêt ACPI.

## Ce que nous avons compris

- `vmbr10` isole les workloads au niveau L2 sur chaque nœud ; donner une IP et un NAT au bridge fournit
  un accès sortant, pas une connectivité entre nœuds.
- Le stockage `zfs-lab` provisionne les disques en thin : la taille déclarée n'est pas consommée d'avance.
- Le Guest Agent est un canal virtio-serial entre QEMU et l'OS invité : il permet à Proxmox de lire
  l'OS, le hostname et les IP de la VM, d'y exécuter des commandes et de l'arrêter proprement.
- Un changement de matériel virtuel (ajout du canal de l'agent) ne s'applique qu'au prochain démarrage
  de la VM par Proxmox.
- Un conteneur n'a pas de kernel : `uname -r` y renvoie le kernel de pve02. Il démarre en moins d'une
  seconde et consomme environ 15 fois moins de RAM que la VM pour le même Debian 13.
- Un conteneur non privilégié décale ses UID (root du CT = UID 100000 de l'hôte) : un root compromis
  dans le CT n'est pas root sur l'hôte.
- Sur ZFS, une VM reçoit un zvol (périphérique bloc) et un conteneur un dataset monté avec `refquota`.
- Un template est une VM figée dont le disque devient `base-*`, en lecture seule : on ne le démarre
  plus, on le clone.
- Cloud-Init sépare l'image (identique pour tous) de la personnalisation (hostname, utilisateur, clé,
  IP), fournie par Proxmox sur un lecteur dédié et appliquée au premier démarrage.
- Un full clone copie tout le disque et devient indépendant du template, au prix de l'espace disque.
